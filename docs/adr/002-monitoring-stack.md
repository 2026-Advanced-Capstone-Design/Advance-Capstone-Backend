# ADR 002 — 모니터링/관측 스택 선택

- 상태: 채택됨 (Accepted) — Phase 1에서 구현·배포 완료
- 작성일: 2026-07-02
- 관련: [REFACTORING_PLAN.md Phase 1], `monitoring/README.md`, [troubleshooting.md](../troubleshooting.md) (2026-07-02 사례)

## 맥락 (Context)

리팩토링의 대전제는 **"먼저 측정 → 개선 → 같은 기준으로 재측정"** 이다. 그러려면 개선 전후를 객관적으로 비교할 관측 수단이 있어야 한다. 그러나 현재 시스템은:

- `spring-boot-starter-actuator`/micrometer/prometheus 의존성 없음 → **애플리케이션 지표 수집 수단 0**
- 로그는 컨테이너 stdout에만 흩어짐 → 중앙 수집·검색 불가
- NHN클라우드 서면평가(2026-05-27)의 지적: **"로그/모니터링 기반 객관적 근거 부족", "성과 수치의 검증 환경 모호"**

제약 조건:
- 운영 인스턴스가 **t2.micro (RAM 1.9GB)** 단일 노드. 앱 스택만으로 이미 메모리 여유가 수십 MB 수준.
- 개인/팀 캡스톤 예산 → **월 고정 구독료 부담 최소화**.
- 데이터 소유·학습 관점에서 인프라를 직접 구성해보는 경험 자체가 목표(면접 대비).

## 결정 (Decision)

**자체호스팅 Prometheus + Grafana + (Loki) 스택**을 채택한다. 단, 메모리 제약을 고려해 **2단계로 나눠 배포**한다:

1. **경량 스택 (`monitoring/simple/`, 현재 배포)** — Prometheus + Grafana 2개 컨테이너(각 `mem_limit: 256m`). 백엔드 애플리케이션 지표 관측이 목적.
2. **풀 스택 (`monitoring/docker-compose.monitoring.yaml`, 유예)** — 위 + Loki/Promtail(로그) + node-exporter/cAdvisor(호스트·컨테이너 자원). 메모리 여유 확보(스왑 증설/인스턴스 업그레이드) 후 도입.

부가 결정:
- 지표 수집: 백엔드에 actuator + micrometer-registry-prometheus 추가, `/actuator/prometheus` 노출.
- **모니터링 스택은 앱 compose와 별도 파일**로 두고 앱 네트워크에 `external`로 합류 → [ADR 근거는 아래 "파일 분리" 항목].
- 표준 대시보드(JVM/Node/cAdvisor)는 방대한 JSON을 저장소에 넣지 않고 **커뮤니티 대시보드 ID import**(4701/1860/19908)로 운용.

## 대안 비교 (Alternatives)

### 관측 스택 선택

| 대안 | 월 비용 | 메모리 부담(자체노드) | 커스터마이즈 | 학습/경험 가치 | 판단 |
|------|---------|------------------------|--------------|----------------|------|
| **자체호스팅 Prometheus+Grafana (채택)** | 무료(인스턴스 자원만) | 있음(관리 필요) | 높음 | **높음** (직접 구성) | ✓ 예산·경험 목표에 부합 |
| **Grafana Cloud (SaaS)** | 무료 티어 후 유료 | 없음(원격) | 중간 | 중간 (관리형이라 내부 이해 얕음) | △ 자원은 편하나 비용·학습 아쉬움 |
| **Spring Boot Admin** | 무료 | 낮음 | 낮음(스프링 한정) | 낮음 | ✗ 스프링 앱만 대상, 시계열/로그/알림 부족 |
| **CloudWatch(AWS)** | 사용량 과금 | 없음 | 중간 | 중간(AWS 종속) | △ Phase 5에서 보조로 병행 검토 |

→ **비용 0 + 커스터마이즈·학습 가치 최대** 라는 이유로 자체호스팅 선택. (Saast[Grafana Cloud]는 Phase 5에서 "관리형 대안 경험" 차원에서 재검토 여지)

### 배포 범위 — 풀 스택 vs 경량

t2.micro(1.9GB)에 풀 스택(컨테이너 6개, 합산 ~1GB)은 앱과 공존 불가. 반면 경량(2개, ~512MB)은 스왑 2GB 병행 시 기동 가능.
→ **"관측이 아예 없음"보다 "핵심 지표만이라도 있음"이 낫다**는 판단으로 경량부터 배포, 로그/자원 지표는 유예.
※ 자원 절약은 **컨테이너 수를 줄여서** 얻는 것이지 파일 분리와 무관 (메모리는 컨테이너/호스트 단위로 소비됨).

### 앱 compose에 통합 vs 파일 분리

| | 통합(한 파일) | 분리(채택) |
|---|---|---|
| 설정 복잡도 | 낮음(네트워크 자동 공유) | 높음(external 네트워크 이름 정합 필요) |
| 앱 재배포 시 모니터링 | **같이 재시작/중단됨** | **독립 유지** (장애 관측 지속) |
| 배포/롤백 diff | 섞임 | 앱=앱, 관측=관측 분리 |
| 데이터 볼륨 수명 | 앱과 얽힘 | 독립 |

→ **생명주기 분리**(앱이 죽는 순간에도 모니터링은 살아 관측)를 최우선 가치로 두어 파일 분리 채택. 비용으로 network `external` 정합 이슈를 감수(→ troubleshooting 사례 2에서 실제 발생).

## 트레이드오프 (Consequences)

**얻는 것**
- 개선 전후 before/after를 같은 대시보드로 객관 비교 → 리팩토링 성과의 "검증 환경" 확보(면접 피드백 직결).
- 비용 0, 인프라 직접 구성 경험.
- 앱과 독립된 관측 → 앱 재배포 중에도 지표 연속성 유지.

**감수하는 것**
- 자체호스팅 = **운영 책임**(업데이트/디스크 보존기간/장애 시 복구)을 직접 짐. → Prometheus `retention 7d`로 디스크 방어.
- 단일 노드라 모니터링이 앱과 **자원을 경쟁** → `mem_limit` 필수, 로그(Loki)·자원지표(cAdvisor)는 유예.
- 파일 분리로 인한 **external 네트워크 이름 정합** 복잡도(`<프로젝트명>_<네트워크명>` 규칙 숙지 필요).

## 검증 결과 (2026-07-02)

- 경량 스택 EC2 배포 → Prometheus `target health="up"`, Grafana 대시보드 6패널 중 5개 실데이터 확인.
- 관측된 커스텀 지표: `ai_analyze_request_*`(AI 호출 지연 Timer), `executor_*`(스레드풀 큐/활성), `cache_gets_total`(캐시 히트율).
- 미도입(Loki 유예)으로 "에러 로그율" 패널만 no-data — 의도된 상태.
- 상세 시행착오: [troubleshooting.md](../troubleshooting.md) 사례 1~4.

## 후속 (Follow-up)

- 메모리 여유 확보 시 풀 스택(Loki/Promtail + node-exporter/cAdvisor) 승격.
- Phase 4에서 Prometheus Alertmanager로 임계치 알림 추가.
- Phase 5에서 CloudWatch 병행 여부 재검토(관리형 대안 경험).
